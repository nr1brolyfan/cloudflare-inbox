# Cloudflare Inbox

An Effect-native email inbox running on Cloudflare. The application uses a TanStack Start Worker as its public origin and a private Effect backend Worker connected through a Cloudflare service binding.

## Requirements

- Bun 1.3 or newer
- A Cloudflare account for deployed environments

## Development

Install dependencies and start the complete local Cloudflare resource graph:

```bash
bun install
bun run dev
```

The local services use stable addresses:

```text
Website: http://localhost:1337
Backend: http://localhost:1338
```

`GET http://localhost:1337/api/health` verifies the Website to Backend service binding. `bun run dev:vite` starts only the TanStack Vite application and does not provide Cloudflare bindings.

Auth requests are served from the public origin under `/auth/*` and forwarded to the private Backend Worker. During `alchemy dev`, effect-auth writes rendered auth messages to the app-owned D1 `DevEmailStore`. Open `http://localhost:1337/dev-email-inbox` to inspect OTP codes and action links; the route and private Backend API both fail closed outside local development. Credential-bearing messages are never written to logs or telemetry. Completion links keep their challenge and secret in the URL fragment, which browsers do not send to the Website Worker, and remove the fragment immediately after hydration. The effect-auth Core API contract includes email OTP, magic link, session, password sign-in, registration, and reset endpoints, but application-owned handlers currently deny public password sign-up and first-password enrollment until the recovery-safe v1 flow tracked in `TODO.md` is complete. Password change and reset enforce a 12-character minimum.

The D1 control plane stores the mailbox registry, globally unique mailbox addresses, mailbox membership projection, user preferences, and effect-auth's scoped grants. Application queries use Effect-native Drizzle over `@effect/sql-d1`; raw D1 is isolated to atomic batches because D1 does not expose transactions through its Effect driver. `app_mailbox_member` is used only to discover a user's mailboxes; effect-auth role and permission grants remain the authorization source of truth. Inbound routing validates Cloudflare's SMTP envelope recipient, normalizes only its DNS domain, and resolves an enabled address on an active mailbox before selecting a `MailboxDO`; MIME `To` headers are never routing evidence. The original MIME stream is then written append-only to private R2 with bounded envelope metadata and confirmed before the email event completes, so downstream processing never precedes durable raw storage. A Cloudflare Workflow instance with the same ingest ID starts only after that confirmation, records the durable `raw_stored` checkpoint, verifies the immutable R2 object, and parses it through a memory-bounded `postal-mime` adapter. The durable parsed manifest contains normalized message fields and attachment metadata but never binary content or storage keys. The Workflow reparses the immutable raw object before attachment storage, requires the second manifest to match the durable one, and writes attachment bytes append-only under deterministic R2 keys with SHA-256 and canonical metadata verification on retries; CID remains validated message metadata rather than part of the storage key. A final trusted Workflow step commits the message, attachment metadata, private ingest mapping, FTS update, and `ready` processing state in one MailboxDO SQLite transaction. The canonical ingest ID is the idempotency key: exact retries return the original message ID, changed payloads conflict, and separate SMTP ingests remain distinct even when they reuse an RFC `Message-ID`; RFC references are used only as conservative threading evidence. MailboxDO also records monotonic `raw_stored`, `parsing`, and `attachments_stored` checkpoints plus sticky terminal failures. Transient R2 and DO errors use bounded exponential Workflow retries, deterministic MIME and integrity failures skip automatic retry, and a late failure write can only resolve to the exact already committed message rather than overwrite `ready`. A protected replay accepts only mailbox, ingest, and operation IDs: MailboxDO atomically reopens an eligible failure, increments its execution fence, and durably assigns a fresh Workflow instance before the same immutable raw MIME is read again. Delayed checkpoints, failures, and commits from older executions are rejected, while repeating the replay operation safely recovers the same prepared instance after ambiguous responses. Each logical mailbox maps by canonical mailbox ID to a SQLite-backed `MailboxDO` data-plane instance using Effect-native Drizzle and synchronous SQLite transactions. Versioned migrations run atomically before that instance accepts RPC calls. Mailbox initialization seeds stable system folders; custom folder and label changes use version checks and soft deletion, while create-operation results are durably replayed by operation ID. Messages and threads are read from canonical snapshots with bound keyset cursors; scheduling consumes a draft atomically into an immutable outbound message and versioned delivery record.

Live inbound admission validates Cloudflare's declared raw RFC 822 size first and rejects values above the shared 10 MiB limit before address decoding, routing, ID/time generation, R2, or Workflow. This trusts validated Cloudflare transport metadata without consuming the stream; it does not infer an arbitrary untrusted stream's size, and `FixedLengthStream` still verifies declared-versus-actual bytes while R2 consumes the upload. Rejection telemetry adds only a closed reason and, for oversize mail, the fixed limit to the existing numeric raw-size span attribute.

Child-resource authorization resolves mailbox and folder ancestry from canonical `MailboxDO` SQLite tables through the `TrustedMailResourceResolver` port and the MailboxDO resource-lookup protocol before checking permissions. Narrow mailbox repositories remain operation-specific data-plane ports rather than one authorization authority. Folder scopes include both mailbox and folder identity, preventing grants from crossing mailbox boundaries when local folder IDs match. Mailbox routing hints supplied by callers select an active control-plane mailbox's corresponding `MailboxDO` but are never used directly as authorization evidence. The migration introducing qualified scopes invalidates legacy bare folder grants because they cannot be mapped to a mailbox safely.

Private application handlers derive `CurrentSession`, `CurrentActor`, and `CurrentPrincipal` by validating the incoming session cookie directly against D1. Client-provided user or session identifiers are never accepted as authorization evidence.

Outbound sends use a server-authoritative undo window, immutable mailbox snapshots, and a dedicated Cloudflare Email Sending binding. The delivery tracker distinguishes provider acceptance from recipient delivery: `accepted` means Cloudflare accepted and queued the message, while only a later `delivered` event may confirm recipient delivery. Unknown provider outcomes become `indeterminate` and are never retried automatically because another submission could duplicate the message.

Mailbox owner bootstrap derives the owner from an unrestricted validated session and creates the singleton `primary` mailbox, its initial inbound address, discovery membership, and scoped owner grant in one D1 batch. The finite application-owned control-plane command inventory repeats token binding, database-time session and grant expiry, fail-closed requirement shape, operation authorization, and expected state inside the same batch as the guarded write, receipt, and audit, closing the change-between-check-and-write race without treating membership rows as authorization evidence. Public account-recovery completion uses exact proof authorization instead of a prior session. Generic effect-auth bookkeeping, ephemeral ceremony starts, development storage, AI audit records, migrations, and `MailboxDO` SQLite are separate persistence categories rather than exceptions hidden inside this contract.

Administrative control-plane audit events use a versioned, metadata-only contract with closed action, reason, resource, tenant-scope, and change taxonomies. Administrative operation IDs are opaque UUID v4 values rather than caller-selected text. D1 constraints enforce those relationships, deterministic event IDs bind records to operation provenance, and triggers reject updates, deletes, and conflict replacement. Mailbox owner bootstrap and display-name rename additionally store an immutable, actor-scoped, state-bound typed result receipt in the same atomic D1 batch, so exact replays and unknown commits can return the original result while changed operation intent is rejected. Migration 1022 snapshots each valid historical V1 bootstrap address into a sealed immutable intent marker; new bootstraps instead write one V2 address companion, and receipt decoding fails if a bootstrap has zero or both intent sources. During rolling deployment, a temporary trigger gives an old writer a V1 marker and exact V2 insertion promotes that marker atomically; ORG-006 removes this bridge after old writers can no longer exist. Their authenticated receipt readback is available through Backend and Website adapters. External recovery identity enrollment and verification now use the same exact-replay algorithm with a closed typed receipt, operation availability guard, unknown-commit recovery, and authenticated no-store readback. The receipt table contains no email address: actor-scoped readback reconstructs immutable address fields by joining the canonical recovery identity. Verify receipts bind only the canonical HMAC of the supplied challenge secret, never plaintext, and do not expose that digest publicly. Administrative audit events remain address-free. A failed audit or receipt insert rolls back the mutation, while rejected authorization or session checks write neither. Audit and receipt contracts exclude message content, request bodies, headers, cookies, plaintext credentials, plaintext secrets, tokens, and generic JSON payloads.

The signed-in Website invokes mailbox operations through TanStack Start server functions. The Website forwards only selected request metadata over the private `BACKEND` binding; the Backend independently enforces the exact public origin, validates the session cookie, and maps domain failures to cause-free HTTP errors. Inbox navigation discovers the active mailbox from the D1 membership projection, then separately requires `mailbox.read` before returning the mailbox name, folder counts, or labels. Folder and label data comes from validated `MailboxDO` directory reads, and the aggregate response rejects any child carrying a different mailbox identity. Message lists require mailbox-scoped `message.read` or `folder.read` on the resolved folder; label views require mailbox-scoped `message.read`. Thread links carry an anchor message that is resolved and authorized before bodies are loaded, preventing a selected folder or label from being used to open an unrelated thread. Thread hydration is SQL-bounded to the latest 50 messages, and folder-scoped reads authorize every returned message. The browser thread projection contains plain text and attachment metadata but no raw HTML body, storage keys, or attachment bytes. HTML preview uses a separate, independently authorized same-origin iframe navigation; Backend parses the body into an inert document, and Website responds with an empty iframe sandbox, restrictive HTTP CSP, no referrer, and no-store caching.

Owner bootstrap is a sensitive ownership mutation and requires authentication evidence no older than five minutes under policy `control-plane-sensitive` version 1. Password and passkey completion both rotate the opaque session token, commit a new HttpOnly cookie, and require the browser to submit the bootstrap action again. A basic session cannot enroll its own step-up factor, and password reset starts only for accounts that already have an active password credential. Magic links, email OTP, recovery codes, stale evidence, non-UV passkeys, and sessions with unmet requirements do not satisfy the policy. The D1 bootstrap batch independently evaluates the same evidence window and session expiry against SQLite execution time together with the token-bound session predicate before writing the mailbox, address, membership, or owner grant. The policy is reusable by future domain, address, grant, transfer, and ownership commands.

Authenticated recovery-code rotation requires an unrestricted token-bound session, recent non-recovery password or UV-passkey evidence, and a verified external recovery identity. The browser retains a caller-generated administrative operation ID across step-up and network retries, while each explicit fresh rotation receives a new ID. Before generating one-time material, the service reads an actor-scoped immutable receipt and snapshots the exact active set or its absence. One guarded D1 batch fences that expected state, revokes the previous active set, stores ten hashes, and writes the typed receipt plus metadata-only auth audit atomically. First success returns the receipt and exactly ten plaintext codes once; replay, authenticated `no-store` readback, concurrent same-operation recovery, and committed unknown-outcome recovery return only the receipt. If an ambiguous browser request committed but its response was lost, the UI states that the replacement committed and the codes cannot be recovered, then offers a fresh operation rather than claiming old codes remain valid. Codes are not administrative step-up evidence. Public recovery requires both a short-lived external-email link and one unused code, then issues a 15-minute session restricted to UV passkey remediation. Completion carries a caller-generated operation ID and an independent browser-held 256-bit readback secret; one guarded D1 batch consumes the exact flow and code, creates the restricted session, appends metadata-only audit, and writes an immutable proof-bound receipt. Exact replay and public POST readback return only a privacy-safe `no-store` receipt and never a cookie or bearer value. Only the first unambiguous completion response can set the restricted HttpOnly cookie; if proof-bound readback confirms a lost response committed, the UI explains that remediation was entered but the one-time session cannot be recovered and directs the user to restart with another unused code. The final atomic remediation batch installs the new passkey and unrestricted session, replaces the primary email login authority with a recovery-passkey identity, revokes prior sessions and sign-in factors, rotates the hash-only code set, and appends metadata-only audits. Secret links use URL fragments, production delivery is detached with Workers `waitUntil`, and recovery responses use `no-store`. `SAFE-002` remains open for direct denial/conflict/HTTP test gaps and depends on the remaining operation-contract work owned by `SAFE-006`, as recorded in the company-mail plan.

The pinned SimpleWebAuthn verifier and passkey option, verification, and credential-management services use the maintained D1 store. WebAuthn policy is derived only from validated `PUBLIC_ORIGIN`: exact origin, hostname-only RP ID, discoverable credentials, required user verification, and no attestation. Public passkey registration start and finish are enabled only for an unrestricted signed-in user with five-minute step-up evidence and the same verified external recovery identity throughout the ceremony. Finish verifies the signed browser response and atomically rechecks the token-bound session, step-up evidence, recovery identity/version, challenge metadata, and credential uniqueness before consuming the challenge, inserting the credential, and appending a metadata-only auth audit event. Discoverable passkey sign-in accepts no caller-selected user ID, credential list, or challenge metadata. Finish requires a purpose-bound challenge, active credential, active user, verified external recovery identity, exact RP/origin, and UV before completing the normal AuthFlow pipeline; account and recovery failures are exposed only as invalid credentials. Passkey step-up requires an unrestricted authenticated session and verified recovery, binds its challenge to the session ID, current token-generation hash, and `control-plane-sensitive` policy version, then uses `assureAndRotate` to append UV passkey evidence and rotate the bearer token. Signed-in users can list and revoke credentials through an application-owned privacy-safe API that exposes only the opaque credential record ID and creation/last-use times, never the WebAuthn credential ID, public key, sign count, transports, or metadata. Revocation requires recent step-up and verified external recovery, protects the final active passkey, atomically rechecks the token-bound session and all policy predicates, and writes the revocation, immutable UUID operation receipt, and metadata-only audit event together. Exact replay returns the stored receipt without repeating step-up, and an unknown commit is resolved by authenticated receipt readback. Recovery-code generation and public two-proof recovery routes are enabled; their remaining plan gaps are verification and operation-contract DoD, not route availability.

External recovery addresses are structurally separate from effect-auth login identities in `app_external_recovery_identity`, so generic password, OTP, and magic-link lookups cannot treat them as login authority. The shared purpose-aware recovery-safe policy rejects the fail-closed resolved managed domain, every mailbox route, verified recovery duplicates, and unexpired pending recovery duplicates using a conservative lowercase comparison key; external recovery enrollment additionally rejects active login identities, while login initiation may resolve its matching active login identity. An unverified recovery reservation stops blocking the user, address, and route when its 30-minute challenge expires. Decorated effect-auth services enforce this policy before email OTP, magic-link, email-verification, and password-reset starts, including verification initiated internally after password sign-in. D1 migration 1017 closes challenge-versus-route races: a newly recorded route invalidates later consumption of an unconsumed email proof, while a consumed proof reserves its target only until expiry. Authenticated external recovery enrollment requires the five-minute sensitive-operation step-up and sends a dedicated verification link whose challenge credentials exist only in the URL fragment. Verification requires the same signed-in user, re-runs the policy, and atomically consumes the challenge, advances the identity version, and appends a metadata-only administrative audit event. Public two-proof recovery also uses this policy and installs replacement login authority only after restricted second-passkey remediation. Public password sign-up remains explicitly denied pending its separate v1 task. Invitation acceptance belongs to `INV-010`, and full future shared address/route mutations to `ADDR-022`.

Every environment requires the values documented in `.env.example`. `PUBLIC_ORIGIN` must be the exact Website origin, and `AUTH_EMAIL_FROM` must use a domain configured for Cloudflare Email Routing in production. `MAILBOX_BOOTSTRAP_OWNER_EMAIL_ALLOWLIST` is a non-empty JSON array (at most 32 entries) of canonical verified email identities allowed to claim the singleton mailbox. `MAILBOX_INITIAL_ADDRESS` is the distinct canonical initial route injected only by the Backend; it is also the trusted managed-domain continuity claim before bootstrap. After bootstrap, recovery-safe policy prefers a current persisted `MailDomain`, falls back to the retained primary route, requires every available claim to agree, and fails closed on malformed, ambiguous, missing, or disagreeing storage. Each auth secret must be a separate high-entropy value. Alchemy binds these values as Worker secrets.

Public account-recovery start applies exact IP and email buckets over ten-minute windows and a deterministic 500 ms minimum response floor. Unknown addresses, disabled users, accounts without an unused code, normal recovery-safe policy denials, and delivery failures return the same accepted body; eligible starts create one ten-minute purpose-bound flow and detach exactly one production send through Worker `waitUntil`. Storage failures, corrupted rows, and other internal dependency failures are not hidden as eligibility outcomes: they return only a sanitized generic 500. The Website `/auth/*` proxy marks every forwarded success, error, and rate denial `private, no-store` with `pragma: no-cache`, while preserving intentional authentication cookies. Recovery remediation accepts only the exact capability list `["second-passkey"]`; overbroad, duplicate, unrelated, empty, and unrestricted sessions fail before the handler and in its transactional D1 predicate. The versioned `mailbox-session-requirements` matrix covers all 19 current mailbox endpoint identifiers as `unrestricted-only`; unknown operations, unfinished requirements, malformed claims, and dangling recovery capability containers fail closed before mailbox handlers with one sanitized denial. This closes `SAFE-002`, `SAFE-003`, and the generic initiation boundary in `SAFE-013`.

## Observability

Cloudflare Workers Logs and native tracing are enabled for both Website and Backend, including invocation, service binding, D1, R2, Durable Object, and fetch spans collected by the platform. Website-to-Backend auth, health, and mailbox calls add Cloudflare custom spans with sanitized method and route-family attributes. Every Backend request receives a server-generated UUID request/correlation context in the request-scoped Layer graph and emits one structured `backend.request.completed` event with status, outcome, duration, a closed route family, and validated Cloudflare ray metadata. The event excludes raw paths and resource IDs, query strings, headers, bodies, cookies, tokens, email content, user agent, referer, and full IP. Caller-provided request/correlation headers are ignored; controlled cross-service propagation remains future work. Effect application logs use structured console output in deployed environments so Workers Logs can index their fields.

Local Backend Effect logs and spans can additionally be sent over OTLP/HTTP to Motel. Start Motel, use the base URL reported by the daemon as `OTEL_EXPORTER_OTLP_ENDPOINT`, and then start the application:

```bash
motel start
OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:27686 bun run dev
```

The Backend builds OTLP log and trace exporters in the request scope. Alchemy closes that scope through `ctx.waitUntil`, ensuring buffered telemetry is flushed without delaying the response. Effect metrics are intentionally not exported per request; production infrastructure metrics come from Cloudflare.

Run `bun run generate:auth-migrations` after changing `@effect-auth/core`. Committed migrations are verified automatically by `bun run check`. Because migration 1017 recognizes the vendor's credential-bearing challenge types and metadata keys, every effect-auth upgrade also requires an explicit compatibility review of that interlock.

Alchemy runs the mail-domain configuration preflight through its own `ConfigProvider` before provisioning, including deployments using `--env-file`. V1 accepts ASCII domains and canonical A-labels only; Unicode U-label input requires a future versioned profile. This check does not yet compare configuration with the persisted primary domain; that remains part of `ORG-009`.

Production deployment uses Alchemy's Cloudflare state store. Local development sets `ALCHEMY_STATE=local` and keeps generated state under the ignored `.alchemy` directory.

## Structure

```text
alchemy.run.ts                 Cloudflare resource graph
src/modules/<context>/         bounded contexts and local hexagonal architecture
src/apps/<runtime>/            Worker, Durable Object, Workflow, and Website roots
src/platform/<capability>/     Cloudflare, control-plane D1, and observability support
src/shared/                    minimal context-neutral semantic kernel
src/routes/                    TanStack Start framework routes
src/auth/schema/               generated effect-auth schema exception
tests/{modules,apps,platform}/ production-path-mirrored tests
tests/integration/             explicitly approved cross-module integration suites
tests/support/                 shared test-only helpers and Layers
```

Architecture policy is enforced by `bun run check:architecture`. Production code uses only the documented roots and framework exceptions. Tests under managed roots mirror their production path and filename; the small allowlist under `tests/integration/` is reserved for suites that deliberately span several production modules.

Passkey enrollment now uses an application-owned browser ceremony that preserves one caller-generated UUID operation ID from start through finish and retry, then rotates it after confirmed success so an explicit next enrollment is a new operation. Normal and recovery-remediation finish first derive a privacy-keyed client-intent digest over the full recursively canonicalized decoded browser credential. A stored receipt can bypass fresh rate limiting only after actor, mode, challenge, readback proof, and client intent match; changed client intent is rejected before WebAuthn verification. A fresh operation runs current prerequisites and rate limiting before verification. Verification then derives a separate privacy-keyed digest over every persisted verified credential field, and replay succeeds only when that digest also matches. Fresh mutation atomically consumes the exact operation-bound challenge, inserts the credential, required audits, and an immutable typed receipt containing both digests but no raw WebAuthn data; remediation additionally binds the replacement identity, unrestricted session, and ten-code set. Normal authenticated POST readback requires the operation ID, challenge ID, and original browser credential and is receipt-only and `no-store`. Recovery binds an independent browser-held 256-bit readback secret by HMAC; only first unambiguous success returns the new cookie and ten plaintext codes. After the old restricted session is revoked, the supported recovery transport is the dedicated rate-limited public POST readback bound to the proof, challenge, and original browser credential, not the restricted finish endpoint; it returns receipt only. A confirmed ambiguous commit is shown as committed without claiming authentication and directs the user to sign in with the new passkey and rotate codes. Receipts contain only the opaque application credential record ID and safe result metadata, never raw WebAuthn credential ID, public key, sign count, transports, client payload, recovery plaintext, session token/cookie, email, or generic JSON. Passkey authentication, sign-in, step-up, and revocation retain their existing contracts.

The source-layout and dependency migration to this structure is complete. That architecture milestone does not imply completion of the organization, domain, stable-address, or multi-mailbox product work tracked in `PLAN-FIRMOWEJ-POCZTY.md`.
